# 成员分析维护手册

更新：2026-09-06。负责维护步骤；产品边界见根 AGENTS，设计见 [design-spec](design-spec.md)，发布见 [release-policy](release-policy.md)。文档分工与历史入口见 [README](README.md)。

## 1. 通用流程

1. 查看工作区状态和相关 diff，保留已有修改。只读取任务需要的文件，不遍历玩家数据。
2. 确定受影响的行为、数据和回滚方式；小修复不强制写 RFC。重大跨层变更先在 README 简述方案，复杂且长期使用的设计可独立成文。
3. 优先修改功能自有目录。上游接入点与预算读 `patch-manifest.json`；实际数量由检查脚本计算，不把历史 9/9 当成当前实测值。
4. 保留公开接口；涉及数据变化时先定义兼容与迁移。测试应保护实际行为和边界，不为每次改动强制新增测试或先拆文件。
5. 按下表验证，记录实际结果和未覆盖项。修复缺陷后重新验证受影响部分。
6. 更新规则所属文档及 README 中的简短维护条目。清理仅限本次创建、已确认不再需要的临时资源；不删除用户缓存、现有包或真实 userData。

## 2. 按影响选择检查

| 修改范围                     | 最低检查                                                                                  |
| ---------------------------- | ----------------------------------------------------------------------------------------- |
| 仅文档                       | 路径/链接、规则冲突、格式；改 Skill 时运行其校验器                                        |
| 局部逻辑或修复               | 相关行为/边界测试、受影响类型检查；跨层时补集成验证                                       |
| UI 或图表                    | 上项，以及设计规范第 9 节的运行态、八主题和人工截图确认                                   |
| 指标、数据契约或数据库       | 计算边界、旧数据兼容、未知版本拒绝、迁移失败恢复；相关 worker/IPC 集成                    |
| 共享模块、上游同步、依赖升级 | 全量 Vitest、node/web 类型检查、生产构建、受影响原生运行态及接入点检查                    |
| Python/worker/打包布局       | worker contract、真实 sidecar 集成、重建包及 hash、隔离 userData 启动/取消/退出、产物扫描 |
| 安全或隐私                   | 最小匿名复现、边界回归、相关文件/产物泄漏检查；立即停止继续扩散                           |

一般代码改动先 focused 后扩大验证；广泛影响不能只跑局部测试。环境缺失写“未运行/受阻”及原因，不能写通过。旧测试数量不作为新任务目标。

从 `akari-src` 使用仓库锁定的 Yarn（版本取 `package.json` / `.yarnrc.yml`）：

```text
yarn typecheck:node
yarn typecheck:web
yarn test
yarn build
node scripts/check-member-analysis-data-leaks.mjs
node scripts/check-patch-surface.mjs --manifest docs/fork/patch-manifest.json
```

命令按范围选择；`build` 不表示发布。Python 路径使用现有环境配置，不写入源码。需要真实 worker 集成时检查 `MEMBER_ANALYSIS_TEST_PYTHON` 对应测试约定。

## 3. 数据和任务维护

- main 管理采集和凭据，worker 只处理规范化数据；renderer 仅调用允许的业务 IPC。
- 持久化数据变化必须有显式版本/兼容策略，不手动修改用户数据库代替迁移。失败恢复旧版完整结果，未知新版本不可静默降级。
- 长任务具有 job id、取消和安全检查点；过期任务不覆盖新结果，临时结果完成后原子发布。
- 玩家数据只在 feature userData 下；现有上游通用日志路径不构成额外玩家数据存储许可。日志仅稳定错误码、阶段、计数和耗时，不记录玩家标识（包括可追踪哈希）、token、原始响应或敏感路径。
- 产品清理必须 preview 后确认，拒绝过期 preview 和并发清理，保留设置和最新发布分析库。测试临时目录清理不是产品清理操作。
- 不增加导出权限；文档中的历史导出方案不授权将玩家数据写到 userData 外。

## 4. 上游、依赖与打包

- 同步前明确目标 SHA、当前基线和接入点；没有目标信息不宣称完成同步。分支默认 `codex/`，用户明确指定名称时遵从。
- 临时同步分支验证后再整合，不直接把未验证的变更合入发布分支；不自行改变 remote、推送或创建 PR。
- 原生模块或 Electron 升级需要真实启动检查。worker 依赖或资源变化需重建 one-dir worker 并更新校验清单，不复制旧 hash 或旧通过数量。
- 打包位置检查 `packaging/member-analysis-builder.yml` 和当前实现；worker 在预期资源路径只出现一次，包内无退役 dashboard、玩家数据或缓存。
- 隔离 smoke 使用本次新建的临时 userData 和合成数据。真实 LCU/SGP 验证只使用 CCB 自己配置的数据，不读取或迁移官方 Akari 数据。
- 官方和 fork 自动更新维持禁用；内部手动升级及未来公开发布条件只在发布规则维护。本地测试不代表干净 Windows、SmartScreen 或杀毒兼容。

## 5. 缺陷与记录

- P0：凭据/玩家数据泄漏、任意 IPC 执行、静默数据破坏、官方 updater 可执行。
- P1：启动/退出失败、孤儿 worker、不可恢复迁移、核心分析不可用或影响结论的严重计算错误。
- P2：局部功能、指标或交互错误且可降级；P3：轻微文案、样式和维护问题。按实际影响升级，不单看文件类型。

README 条目按需要包含：复现与影响、根因/改动、版本/数据影响、实际检查和遗留项。不复用历史“无未解决缺陷”作为当前结论。

| 变化                 | 同步位置                               |
| -------------------- | -------------------------------------- |
| 产品/权限边界        | 根 AGENTS                              |
| UI/交互/分析设计规则 | design-spec；对应 Skill 仅调整执行方法 |
| IPC/版本/兼容        | contract、实现及相关测试               |
| 上游接入点           | patch-manifest 与实际 guard            |
| 发布条件             | release-policy                         |
